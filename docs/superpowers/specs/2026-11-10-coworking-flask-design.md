# Дизайн: сайт коворкинга на Flask (вариант A)

**Дата:** 2026-11-10  
**Статус:** утверждён пользователем  
**Подход:** монолит Flask + SQLite + брони как интервалы `[start, end)`

## Цель

Сайт-визитка коворкинга: посетители **не регистрируются** и **не бронируют онлайн** — смотрят занятость и звонят. Администратор в админке вручную создаёт, подтверждает и отменяет брони после звонка.

На публичной странице для **выбранного дня** по каждому типу мест видно: сколько единиц свободно и **какие именованные единицы заняты в каких слотах**. На публичке учитываются только брони со статусом **`confirmed`**. Статус `pending` на сайте не отображается (слот считается свободным для посетителя).

Первый деплой: **HelioHost** или **PythonAnywhere**; позже перенос на платный хостинг с минимальными изменениями (`DATABASE_URL`, WSGI).

## Архитектура

```
Browser
   │
   ▼
WSGI (HelioHost / PythonAnywhere)
   │
   └── Flask app
         ├── public blueprint (read-only, HTML)
         ├── admin blueprint (session auth)

   │

```

**Вне v1:** Redis, Celery, SPA, публичный JSON API, онлайн-бронирование.

## Каталог (не в БД)

### Тип места

Задаётся **один раз** в репозитории (без UI). Поля:

- `id`, название для сайта
- `granularity`: `hourly` | `daily` | `monthly`
- Для `hourly`: рабочие часы и шаг (по умолчанию 1 час; для переговорных в v1: **09:00–21:00** в config типа)
- Для `daily`: слот = календарный день (локальная TZ)
- Для `monthly`: слот = **календарный месяц** (с 00:00 первого числа до 00:00 первого числа следующего месяца)

### Единица (unit)

Seed в репозитории (без UI): `id`, `type_id`, отображаемое имя, `active: bool`.

### Правила бронирования по типам

| Тип | Интервал в БД | Кто создаёт |
|-----|---------------|-------------|
| Переговорная (`hourly`) | Один или несколько **подряд часов** в одной брони | Админ |
| Стол (`daily`) | Один или **несколько календарных дней подряд** в одной брони | Только админ |
| Стол (`monthly`) | Целый календарный месяц | Только админ |

Публичное и админское поведение согласовано: **все** брони создаёт только администратор; «несколько дней подряд» — не отдельный канал, а длинный daily-интервал.

## Модель данных

### Таблица `booking`

| Поле | Описание |
|------|----------|
| `id` | PK |
| `unit_id` | Строковый id из каталога |
| `starts_at`, `ends_at` | Полуинтервал `[start, end)`; хранение в **локальной TZ** (`Europe/Moscow`) единообразно |
| `status` | `pending` \| `confirmed` \| `cancelled` |
| `note` | Опционально (контакт/заметка), **не на публичке** |
| `created_at`, `updated_at` | Аудит |

**Индексы:** `(unit_id, starts_at, ends_at)`, `(status)`.

**Пересечения:** при сохранении запрет пересечения с любыми бронями того же `unit_id`, где `status != cancelled`.

Каталог в SQLite **не** дублируется.

Миграции: **Flask-Migrate (Alembic)**; при деплое `flask db upgrade`.

## Публичная часть

### Маршруты

| Маршрут | Назначение |
|---------|------------|
| `GET /` | Визитка: контакты, CTA «позвонить», ссылка на занятость |
| `GET /availability` | Занятость на выбранный день |

### Выбор даты (7 кнопок)

- Горизонтальная полоса из **7 кнопок**: слева **сегодня**, далее +1…+6 дней (локальный календарь, TZ приложения).
- На каждой кнопке **столбик**: число / краткий месяц («ноя») / день недели («пн»).
- Активная кнопка — выбранный день; под полосой — **одна** таблица занятости **только на этот день**.
- Query: `GET /availability?date=YYYY-MM-DD`. Без параметра — сегодня.
- Если `date` **вне** окна [сегодня … сегодня+6] → **редирект** на `/availability?date=<сегодня>`.
- При наступлении нового календарного дня окно пересчитывается (сегодня снова слева).

**v1 UX:** клик — полная перегрузка с `?date=...`; на мобильных — **CSS scroll-snap** для горизонтальной полосы; без JS-карусели и без htmx.

### Отображение занятости

- Блоки по **типу места** (только `active` units).
- **Почасовые типы:** строки — слоты (часы в рабочем дне типа); для каждого слота: занятые **имена единиц**, **свободно X из N**.
- **Дневные типы** (в пределах выбранного дня): занят/свободен по единицам или агрегат + список занятых имён.
- **Месячные типы:** на выбранный день показывать, занята ли единица на этот день в рамках месячной брони (пересечение дня с `[starts_at, ends_at)` и `confirmed`).

**Статусы на публичке:**

| status | Публичная занятость |
|--------|---------------------|
| `confirmed` | Занято |
| `pending` | Свободно |
| `cancelled` | Свободно |

Логика: сервис `availability` строит слоты из схемы типа и помечает unit занятым при пересечении с `confirmed`-бронью.

## Админка (`/admin`)

| Маршрут | Действие |
|---------|----------|
| `GET/POST /admin/login` | Логин (env) → сессия |
| `POST /admin/logout` | Выход |
| `GET /admin/bookings` | Список (фильтр: даты, unit, status) |
| `GET/POST /admin/bookings/new` | Создание |
| `GET/POST /admin/bookings/<id>/edit` | Редактирование статуса, note, интервала |

**Форма создания:**

1. Выбор `unit` (группировка по типу).
2. Поля времени **по типу** (серверная валидация):
   - `hourly`: дата, время начала, длительность в часах (или конец).
   - `daily`: дата начала, дата конца (включительно → в БД `[start 00:00, end+1day 00:00)`).
   - `monthly`: выбор месяца → границы календарного месяца.
3. Статус: по умолчанию `pending`; допустимо `confirmed`, `cancelled`.
4. `note` — опционально.

**Безопасность:** `@login_required` на все маршруты кроме login; CSRF (Flask-WTF); секреты только в env.

**Без UI** для типов, схем слотов и единиц — изменения через seed/конфиг и redeploy.

## Ошибки и краевые случаи

- Пересечение на том же unit → ошибка формы, без сохранения.
- Некорректный интервал для типа → flash с понятным текстом.
- Новые брони на неактивный unit → запрет.
- `confirmed` → `cancelled` → место сразу свободно на публичке.
- Нет confirmed-броней на день → сообщение «все места свободны» (или эквивалент).

Логирование 500 в stderr/лог хостинга; без утечки note на публичных маршрутах.

## Тестирование (v1)

- `pytest`, тестовый конфиг, in-memory SQLite.
- Юнит-тесты: `booking_validation`, `availability` (пересечения, hourly/daily/monthly, только `confirmed` в публичной логике).
- 1–2 интеграционных: `GET /availability?date=...` с seed-бронями.

UI-автотесты в v1 не обязательны.
